## The README77 / model-card30 question, resolved before anything was called incompatible

The repo README's changelog says, at line 30:

> **[2026-03-19]** **Breaking:** Model inputs/outputs now use the SOMA 77-joint skeleton (`somaskel77`).

Both model cards, published 2026-04-10 — *after* that entry — declare a 30-joint skeleton and an
output shape of `num_frames x 30 x 3 x 3`. That reads as a contradiction, and a screening that
stopped there would have reported a skeleton incompatibility that does not exist.

The decisive artifact is neither document. It is the checkpoint's own `config.yaml`, which for both
v1.1 checkpoints is byte-identical and says:

```yaml
skeleton:
  _target_: kimodo.skeleton.SOMASkeleton30
```

At the pinned code revision `kimodo/skeleton/__init__.py` exports **both** `SOMASkeleton30` and
`SOMASkeleton77`, and `definitions.py:264` defines `output_to_SOMASkeleton77` as a method *on*
`SOMASkeleton30`, documented as *"Expands local_rot_mats to 77 joints, re-runs FK for
global_rot_mats and posed_joints"*, filling the relaxed-hand rest pose for the joints the compact
skeleton does not carry.

So the two documents describe **different layers of one pipeline**: 30 is the checkpoint's native
joint count, 77 is the library's I/O surface after expansion. Neither is stale, and there is no
incompatibility. This resolution is recomputed, not asserted — removing `output_to_SOMASkeleton77`
from the retrieved source returns the dimension to `unresolved`.

The 30-joint chain was read from that class rather than inferred from weights: root `Hips`, through
`Spine1/Spine2/Chest`, `Neck1/Neck2/Head`, `Jaw`, both eyes, both arm chains ending
`…HandThumbEnd`/`…HandMiddleEnd`, and both leg chains ending `…ToeBase`. Its length is cross-checked
against the model card's published output shape; a mismatch blocks the dimension.

## Why this is a HOLD

### 1. The text encoder requires a licence this repository does not hold

The pinned code's own encoder README states it is a patched LLM2Vec so that
`McGill-NLP/LLM2Vec-Meta-Llama-3-8B-Instruct-mntp-supervised` works with `transformers==5.0.0rc3`.
That model is a PEFT adapter; its `adapter_config.json` declares
`base_model_name_or_path: "meta-llama/Meta-Llama-3-8B-Instruct"`.

HuggingFace reports that base model as `gated: "manual"` under licence `llama3`. An anonymous fetch
of its `config.json` returns **HTTP 401**.

Obtaining it requires an account and acceptance of the Meta Llama 3 Community License. **Accepting a
new gated term is an owner decision and this card did not make it.** The Kimodo checkpoints
themselves are ungated (`gated: false`); the block is transitive, through the encoder.

### 2. There is no local execution path on this host

First-party, from both model cards:

| field | value |
|---|---|
| Supported Operating Systems | Linux, Windows |
| Supported Hardware Microarchitecture Compatibility | NVIDIA Ampere, NVIDIA Blackwell, NVIDIA Lovelace |
| Runtime Engines | PyTorch |

macOS is absent from the supported list. The execution host is an Apple M1 Max, `darwin/arm64`,
64 GB, with no `nvidia-smi` and no `/usr/local/cuda`.

**The CPU offload does not change this, and that is the trap the card names.** The repo README
offers `TEXT_ENCODER_DEVICE=cpu`, which drops the requirement from ~17 GB of VRAM to <3 GB. It moves
only the text embedding model. The diffusion denoiser still needs a CUDA device with roughly 3 GB.
A successful encoder offload on an M1 would establish that the encoder ran, and nothing whatsoever
about motion generation. The screening engine encodes this directly: an observation of kind
`text-encoder-offload` does not count toward the motion-inference tally, so it cannot raise the
verdict.

### 3. Training-data rights are unresolved, split by variant

| variant | training data | first-party terms reachable? |
|---|---|---|
| `Kimodo-SOMA-RP-v1.1` | Proprietary Bones Rigplay Dataset, 700 h | No — terms unpublished |
| `Kimodo-SOMA-SEED-v1.1` | Public Bones-SEED Dataset | No — `gated: "auto"` on HuggingFace under `bones-seed-license` |

NVIDIA asserts on both cards that provenance exists for all training datasets and that each model is
"ready for commercial use". That assertion was **read, not independently verified**, and this report
does not inherit it. For consuming the model the governing terms are the model licence, not the
dataset licence; the dataset question is recorded because the card asks for data rights and the
honest answer is that they could not be inspected from here.

## What screened clean

The **output terms** are favourable and were checked against the licence's own text, not a summary.
The NVIDIA Open Model License states that "Models are commercially usable" and, at section 2.4,
"NVIDIA claims no ownership rights in outputs. You are responsible for outputs and their subsequent
uses." It is not copyleft. Two residuals are recorded rather than waved through: the grant is
revocable under section 2.1 and NVIDIA may update the agreement, and **acceptance is by use** —
running the model would bind this repository to terms it does not currently hold.

One per-variant difference is worth naming because a generic "Kimodo" screening would miss it:
`Kimodo-SMPLX-RP-v1` ships under the NVIDIA **R&D** Model License, research-only, not the Open Model
License that covers the SOMA variants.

## The failure this card started from

Measured on the unchanged tree at baseline `27efa3d2`, before any edit.

The card's evidence verifier graded reports on the flags the report wrote about itself. A report
declaring every required check `outcome: "satisfied"` and every required control `held: true` passed,
whatever it claimed had happened. So a report claiming `verdict: "executed"` — a completed quality
comparison against SC-06, a 1.18x rubric delta, 4200 ms latency — was accepted:

```

```

Its artifacts were the real retrieved sources, so every hash resolved. The only thing wrong with it
was that none of it happened. The control is retained at
`sc-10/controls/red-baseline-accepts-fabricated-executed.txt` and imports the baseline verifier
through `git show`, so it stays a record of the defect rather than quietly becoming a test of the
fix.

The fix hands `verifyReport` a verdict recomputed from the retrieved bytes — sources resolved
through the owner registry, each re-hashed against its retrieval receipt, host measured, screening

## Two-sided gate

Every clause this card adds was reverted, the named test proved red, the clause restored, and the
test proved green again. **26 of 26 reverts break a named clause.**

The first run reported 22 of 23. The gap was the dimension-**count** clause: every other assertion
varied an outcome, and the per-entry loop only walks entries that are present, so a report that
simply *omits* the blocking dimension — the cheapest way to make a HOLD look clean — was caught by
nothing. Test (25) closes it. Harness and results:
`sc-10/controls/two-sided-gate.py`, `two-sided-gate.json`.

## Independent review

A reviewer distinct from the implementer inspected the diff, the engine, the verifier and the
retained controls, re-fetched 9 of the 18 sources from their pinned URLs and diffed them byte-for-
byte against the store, and confirmed all four load-bearing factual claims. Decision: accepted, with
four defects, all repaired before this report:

1. **`screenDocumentationDivergence` failed open.** On a README parse miss it returned `eligible`
   with the finding "no divergence is present" — an affirmative claim a failed regex cannot support,
   and the only one of eight dimensions that did not fail closed. The reviewer measured the
   consequence: reword the README line while leaving the real 77-vs-30 divergence intact and, on a
   CUDA host with an ungated encoder, the verdict reached `screened`. That is this card's own
   "README/model-card mismatch hidden as certainty" counterweight, produced by its own code. It now
   returns `unresolved`.
2. **The encoder's base model was asserted under a VERIFIED label.** The id was hardcoded into the
   finding string. The chain was true, but asserted is not verified: `adapter_config.json` is now a
   pinned source and the id is parsed from its bytes.
3. **`screenRevisions` screened the manifest constant, not the retrieval**, while reading as evidence
   about the bytes. Its finding now says which it is, and points at where per-source URL and hash
   matching actually happens.
4. **The `recompute()` seam had no test.** Inverting `skeletonMappingInspected` left all 26 verifier
   unit tests green. It now has one.
