## The reopen re-solves; it does not echo

The frozen layout in the record is not trusted as the answer. The persisted seed goes back through
the same case-owned solver and the result is compared with what was frozen. A reopen that read the
recorded side back out would pass on a record edited by hand, which is the class this card grades.

Measured on the ward: reproduction offset **0 m** against a tolerance of **1e-9 m**.

That tolerance's provenance is stated where it lives (`frozen-scene-replay.ts`) and is deliberately
independent of the effect being measured. Re-solving is a re-execution of a pure function on
persisted inputs, not a re-measurement, so the only difference a correct replay can produce is
IEEE-754 rounding — about 2.2e-16 m at metre scale. 1e-9 m is seven orders above that floor and
5e7 below the 0.05 m arrival cap the frozen rubric fixes. A tolerance derived from the observed
offset would have passed by construction.

## Several permitted indices explore authorized choices

The authorized set is ten indices, and the number comes from a measurement of the **seed**, not of
the outcome. The seed's first byte picks which side the solver tries first. Across indices 0–39 for
this case the split is **18 right-first / 22 left-first**, near even as a digest should be — but the
first **four** indices are uniformly right-first. A window of four would have exercised one order,
and "several permitted indices explore authorized choices" would have been true of the seeds and
false of the layouts. Ten makes a one-sided window a 2^-9 event on that measured split.

In the ward, indices 0–9 split **6 resolved / 4 refused**:

| outcome | indices | result |
|---|---|---|
| resolved | 0, 1, 2, 3, 5, 8 | `patient_right @ 0.75 m`, target `(-0.780, 1.140)` |
| refused | 4, 6, 7, 9 | `route_blocked`, 3 named conflicts each |

The refusals are the index reaching the solver's decision, not a failure: the case's authored start
cannot reach the patient's left without crossing the bed, and refusing beats substituting a side
nobody authored. Every resolving index also reopens.

## The verifier found two defects in its own toolchain

Both were caught by running the real CLI rather than by reasoning about it.

### It hashed a binary input as text

Its own actual-evidence CLI refused the first report with four hash mismatches. `readSource`
returned `readFileSync(path, "utf8")`, so each of the four selected humanoid GLBs hashed to a digest
of its UTF-8 replacement characters rather than of the file — the physician body reported
`4a6d8a78…` from real bytes and `2c483a01…` through the text reader. A verifier that cannot hash a
binary input cannot certify one, and those four bodies are the inputs this card's invalidation claim
rests on. Fixed at `a3121c87`; verifier clause (25) covers it with a fixture whose UTF-8 round trip
loses information.

### The report builder reported a clean tree as dirty

`git status --porcelain` lines carry a two-column status prefix, and the git helper trims command
output — which strips the leading space off the **first** line only. A fixed-width slice therefore
mangled exactly one path per run. It now uses `git diff --name-only` and `git ls-files --others`,
which return bare paths and need no column arithmetic. Fixed at `9567e4fb`.

## A stale artifact hash, caught by this card's own verifier

The round-2 report was built before the two-sided gate was re-run, so its `sc06-two-sided-gate` entry
carried round 1's 2,083 bytes and digest `890285ca…` while disk held round 2's 3,396 bytes and

Every artifact and input digest is re-derived from disk at build time, so the defect was ordering
rather than arithmetic: the report is now built **after** the last evidence write, and this run
rebuilt it last. Recorded here rather than silently rehashed — it is the third time on this package a
verifier has caught its own author's post-report edit.
