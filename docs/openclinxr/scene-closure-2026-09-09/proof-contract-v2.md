## Why the completion gates change

The inspected code baseline is `bb49e9675cba1f7edfe0f0fd80f798120f5bd46d`. Its components establish useful starting points, not the connected encounter:

- `packages/openclinxr/scenario-runtime/src/initial-scene-spec.ts`, `initialSceneSpecPermitsPromotion`, rejects unmet required assets and precompleted learner tasks but does not reject unmet runtime-owned required starting states.
- `packages/openclinxr/scenario-runtime/src/scenario-runtime.ts`, `advanceScheduledEvents`, adds IDs to the emitted set before returning due events. That alone does not prove an effect was applied or retried after failure.
- `apps/ui-xr/src/main.ts`, `runtimeActorPlacement`, calls `supportedActorPlacementPosition` without exact mounted support observations and logs refusal before returning a position. `initializeRemoteTraceSession` is an actual entry caller that must obey admission.
- `packages/openclinxr/asset-registry/src/bedside-approach-path.ts` checks sampled waypoints at default 0.35 m spacing. Its continuity claim must be tested against an obstacle between samples. `approach-executor.ts` advances a root but does not itself connect a cleared clip to the normal encounter; its contact metric uses absolute world Y rather than a signed floor-frame distance.
- `packages/openclinxr/xr-humanoid-animation/src/locomotion-clip-playback.ts`, `packages/openclinxr/xr-asset-loading/src/generated-loaders.ts`, and the existing main UI caller provide integration seams. Their presence is not proof of actual actor selection, supported pose, approach or stop.
- The public site remains `docs/index.html` and `docs/styles.css`. HTML checks cannot establish video playback, valid media lineage or truthful claims.

Every worker therefore delivers both a behavior test and a separately executed verifier of its actual evidence. A report's existence, a self-declared pass, an already-green regression suite or verifier unit tests on synthetic fixtures cannot close a card. BothyBoard's proof attestation is not a test runner: the landing owner must execute and inspect the required commands.

`tools/openclinxr/evidence/scene-closure/proofs/sc-NN/`

Reading another card's accepted code or evidence does not grant permission to edit it. SC-09 may inspect all reports but cannot repair production code, rewrite prior reports or change the frozen rubric while grading.

Each card must deliver the following future implementation files; the behavior test uses its exact path in the per-card table, and both verifier files live in its own proof directory:

| File | Required function |
|---|---|
| Named behavior test in the per-card table | Exercise the card's real production boundary, normal browser workflow or independent measurement/research operation described below. It must not consist only of verifier fixture tests. |
| `verifier.test.ts` | Test that the evidence verifier accepts a complete valid control and rejects missing, stale, corrupt, contradictory and inappropriate evidence. Synthetic fixtures are allowed only in this suite. |
| `verify.ts` | Read the explicitly supplied actual report, independently resolve and inspect its evidence, recompute applicable assertions and return a nonzero exit code on any unmet required result. |

The fixed completion commands for a worker are these exact templates, instantiated with its number, plus all retained regression commands:

```text
run:pnpm exec vitest run <exact-behavior-test-path>
run:pnpm exec tsx tools/openclinxr/openclaw/assert-contract-live.ts <exact-behavior-test-path> SC-NN-required-behavior
run:pnpm exec vitest run tools/openclinxr/evidence/scene-closure/proofs/sc-NN/verifier.test.ts

```

The owner expands `NN`, the exact behavior test path and every frozen write root into literal arguments on each card. Every behavior test contains an ordinary `it('SC-NN-required-behavior', ...)` with actual required assertions. The existing `assert-contract-live.ts` checks that this title is present as `it(...)` and is not still `it.fails(...)`; it is a source-pattern check, not proof that the test runs or asserts useful behavior. Pair it with the actual Vitest run, inspect real result counts and test source, and reject a title hidden in a comment, skipped enclosing suite or empty callback. `exists:` may additionally name the two reports but is not the decisive gate. No universal `live:` or `changed:` requirement is introduced. A source edit can be required where logically necessary, such as authoring the new case or adding the website presentation; unnecessary asset rewrites or filename churn are not proof. The existing planned SC-00/07 paths in the table become these behavior entrypoints, paired with their card-local verifier; existing regression tests do not replace this behavior-plus-actual-evidence pair.

`verify.ts` must require exactly one explicit `--report` argument and the repeated `--scope` arguments listing every frozen card write root exactly once. Compare their normalized set against the owner-pinned contract, reject omitted/extra/duplicate scopes, and never treat the CLI or report as authority to widen scope. The `--scope` list is a required audit boundary, not a request that every allowed root must change. Audit the actual task-attributed source changes and evidence coverage against these roots and the behavioral exclusions; reject modifications outside scope, including symlink escapes. A broad permitted file does not permit edits to explicitly excluded functions. Missing/unreadable reports, unknown flags, wrong card IDs, unsupported schema versions or report paths resolving outside the expected committed report location must fail. Production verification has no fixture flag, default report, environment fallback to a test fixture, auto-generated successful sample or catch-and-pass mode. It must not generate the evidence it is grading. Verifier unit tests may invoke an exported validation function with fixture data; the completion CLI must resolve actual external evidence through the approved store registry and inspect it.

## Evidence report schema and trust boundaries

The JSON report is a structured index of evidence, not an authority that can declare its own requirements satisfied. Implement a versioned strict schema with these required sections. A field may be inapplicable only where the fixed card contract permits it; explain why. Missing future dependencies are never fabricated as inputs to an earlier card.

| Section | Required fields and semantics |
|---|---|
| `schemaVersion`, `cardKey`, `contract` | Literal supported version and card key; hashes and reachable commit of acceptance, worker, proof and delegation contracts; owning A-row IDs. The verifier's expected A rows and control IDs come from the pinned card contract, not an arbitrary list supplied by the report. |
| `implementation` | Product source commit, clean measured tree identity, accepted dependency baseline, exact task-attributed change commits, capture/tool source commit, exact relevant tracked input paths with byte hashes, runtime/tool versions and platform. List any allowed instrumentation and how it is read-only. No unrecorded dirty production or test changes. |
| `execution` | Task ID, actual command argv, working-tree identity, start/end times, process exit status, test counts including failed/skipped/todo, and references to complete command outputs. Count and inspect required tests; zero tests and skipped required paths fail. |
| `counterweight` | Exact test IDs, baseline or remove-the-fix revision, relevant failing assertion and observed value, passing known-good control, fixed revision and observed result; immutable output references for both runs. Missing files, compilation/setup failure or unavailable server are not a behavioral baseline failure. |
| `encounter` | When applicable: the persisted synthetic case ID/version/hash, approval and bundle IDs/hashes, room/template, actors, exact support/equipment instances and asset/clip/rig/solver hashes, seed/index, run/session/request/replay IDs and requirement/observation revisions. Earlier cards include the facts they actually establish; SC-01 is not required to invent a completed motion run. |
| `observations` | Referenced raw records with units, monotonic times and phase/domain-time mapping, observed instance/body IDs and source/capture method. Store numeric values and actual outcomes, not only `pass`, `ready`, `clipPlayed` or an aggregate percentage. |
| `checks` | One result per contract-required check ID, with observed values, expected predicate or frozen rubric reference, input evidence IDs and any refusal/conflict. Unknown/omitted required outcomes fail. Duplicate IDs, contradictory records and a nonempty encounter reduced to empty requirements fail. |
| `controls` | One result for each mandatory negative/known-good/recovery control, with trigger, expected rejection or preserved behavior, actual observed result and artifact references. A report cannot lower the required set by removing a control. |
| `artifacts` | Stable opaque artifact ID, approved store alias, relative object key, byte count, SHA-256, MIME/type, creation/run identity and source/derivative relation. Media includes duration, dimensions, frame/timestamp/capture-gap facts; telemetry includes sample counts and schema. Paths and hashes must resolve to actual bytes, not promised uploads. |
| `reviews` | Reviewer identity/role distinct from the implementation worker where independence is required; reviewed source/run/hash, actual retrieval and viewing session/time, observations and decision. Machine validation can check binding and completeness but cannot manufacture a visual or qualified clinical judgment. |
| `limits` | Explicit unproven clinical, worn-headset and publication claims; unresolved defects separated from excluded claims. A required engineering failure cannot be relabeled a limitation and pass. Research status follows SC-10's distinct rules. |

For checks whose expected values are compile outputs or measured geometry, recompute from the bound persisted case, actual normalized mounted geometry, recorded observation stream and frozen rubric. Never trust a second copy of the expected value supplied by the same report. Rehash files, parse/validate records, decode media, enforce actor/run/version identity and repeat the card's required observable checks. Test the verifier against a plausible all-green report with its underlying artifacts removed or changed.

The Markdown report explains the result and points to the same JSON evidence index. It is public-safe and must not carry credentials, hidden clinical facts, real personal data, raw trace dumps or private absolute storage paths. A Markdown statement cannot override a failed JSON/command result.

## Actual evidence storage and revision lineage

Use an authorized restricted artifact store outside disposable worker worktrees. The existing durable local volume is valid for same-host execution only when a separate reviewer session can resolve, retrieve, hash and decode the originals. A bare machine-local path promise or ignored work directory is not delivery. A future cross-host run must establish equivalent authorized access before capture. No new cloud service, payment or public upload is implicitly authorized.

Committed reports contain public-safe opaque store aliases and object keys. Before SC-01 produces its first actual evidence, the execution owner creates a restricted local registry and supplies its absolute path via OPENCLINXR_SC_EVIDENCE_REGISTRY to every proof command. Missing/unreadable registry fails; this environment variable is an explicit trusted-store locator, never a fixture fallback. Bind its content hash in receipts; it is owner-controlled and workers may not replace it to admit their fixtures. The execution owner resolves the aliases through that registry; the registry contains the real existing storage root, access/retention owner and retention period. The verifier must reject an unknown alias, traversal/symlink escape, inaccessible object or unapproved public URL. Credentials and private registry contents never enter docs. The report cannot define a new trusted storage root or change the registry to point at its fixtures. SC-07 and SC-09 record independent retrieval receipts. Public media is a separately cleared sanitized derivative, with its own byte hash and source edit ranges.

Avoid self-referential Git hashes: capture a clean product/tool source commit first; store that commit and relevant input-byte manifest in evidence; add evidence reports in a later commit. Do not demand that a report contain the hash of the commit that contains itself. The final landing owner verifies the measured source commit is reachable from the integrated review head and compares all relevant product, test, verifier, build, asset and configuration inputs at that head against their captured hashes. Evidence-only documentation changes may occur afterward. Any changed relevant input requires fresh proof, or a documented independent impact review followed by the affected proofs; an old source commit being an ancestor is insufficient. Verification commands run on the actual integrated head, not a worker's stale checkout or stale package `dist/` output. Scope audit uses the task-attributed commit set against its accepted dependency baseline, reconciled by the integrator with actual patches and integration commits; it must neither accuse prior dependency changes of belonging to this task nor omit a task change by dropping it from the report. Later unrelated cards may be present at the integrated head; the source-input freshness check still covers every relevant consumed input, independently of write-scope attribution.

For downstream handoffs, record accepted upstream report/manifest hashes and exact selected source versions. A later asset substitution, contract change, case edit, rubric revision or runtime repair invalidates dependent evidence. Rebuild changed package exports before cross-package tests. Do not make one blanket assertion that every file in the repository was unchanged; identify the actual consumed input closure, and have the reviewer inspect it for omissions.

## Baseline failure, review and landing

On later authorized execution, a worker first implements the named behavior test and demonstrates the missing behavior against the current applicable baseline or a controlled remove-the-fix variant. The test must reach the relevant boundary and fail an expected observable assertion. A missing future file/export/report, import error, test discovery failure, unavailable server or skipped test does not establish that the old product behavior was rejected. New feature tests may use stable existing interfaces to expose the absent behavior; when a new interface prevents direct baseline execution, retain a behaviorally meaningful remove-the-fix experiment after implementation.

Keep the baseline command/observations, unchanged known-good control and fixed result together. After implementation, required acceptance tests are ordinary passing tests with no `it.fails`, skip, todo, zero-case loop or empty requirement set. Synthetic verifier tests independently prove rejection logic; then execute the actual CLI on the real produced report. A passing synthetic fixture test cannot make the CLI's absent actual report optional.

The review owner must:

1. Inspect changed source and tests to confirm the named production caller/independent operation was exercised and the negative controls test the claimed failure. Inspect the evidence verifier rather than trusting its filename or exit code alone.
2. Integrate serially where roots overlap, build changed package exports, and re-run every listed completion/regression command on the integrated candidate head with the approved actual evidence registry.
3. Recompute source/contract/upstream/artifact hashes; retrieve and inspect real evidence. Require independent visual review for visual claims. An automated observation record does not confer clinical credentials.
4. Resolve every required defect before landing that card. Record source head, exact commands/results, actual report SHA-256 and remaining excluded claim boundaries in the owner attestation. Only then use the normal supported BothyBoard landing mechanism.

## Failure-to-repair and parent closure

When review discovers a defect, identify its A-row owner, exact reproduction and invalidated artifact/report versions. Return the task through the supported board review/repair mechanism. If a frozen/landed card cannot be reopened with the required scope, the owner creates an explicitly linked bounded repair card, holds affected downstream closure and records supersession/dependencies. A worker cannot rewrite its own contract, classify the failing acceptance test out of scope, repair an unrelated owner silently or lower a rubric to get green.

After repair, rerun the owning proof and all affected downstream proof commands and recapture affected evidence. Preserve failed evidence as a failure record; do not replace bytes under an old supposedly accepted hash. A selected asset replacement can invalidate case compilation, calibration, placement, approach, replay, recording and website lineage. The owner records precisely which descendants were invalidated and why unaffected evidence remains valid.

SC-P is a non-executable parent and is never dequeued as an implementation card. Its decisive machine gate is the same direct SC-09 invocation:

```text
run:pnpm exec tsx tools/openclinxr/evidence/scene-closure/proofs/sc-09/verify.ts --report docs/openclinxr/scene-closure-2026-09-09/evidence/sc-09.json --scope <each-exact-SC-09-frozen-write-root>
```

The owner copies the literal complete SC-09 verifier command, including every repeated scope argument, onto SC-P; the parent does not invent a different audit scope or grant itself those implementation rights. Retain `pnpm pages:sync-validate` as a regression check. SC-P has no independent product write scope and cannot pass merely because a report exists or every child is Landed. The owner reads the final A01–A12 matrix, independent retrieval/viewing/replay evidence and control results before parent closure. SC-09 must not accept its own JSON flags as external review evidence.

Technical acceptance includes the bounded engineering bedside target and demonstrated website package. Qualified clinical validation, a worn-headset claim and public deployment remain separate evidence/authorization boundaries; a missing qualification must remain visible rather than be invented by an agent. SC-10 remains a separate research assessment and cannot block or falsely replace A01–A12. These boundaries allow an honest technical completion without pretending a desktop recording proves a clinical or headset outcome.
