# Complementary scene research for OpenClinXR

**9 September 2026 · selected first-party research, not an exhaustive survey**

This supplements the [main brief](../humanoid-scene-layout-research-brief-2026-09-09.md). The useful additions are activity-derived functional constraints, explicit starting-state predicates and independent checks of realized geometry. They strengthen the existing initial-scene planner and bounded placement resolver. No external generator, simulator or learned model is a prerequisite for the prototype.

## Newer leads kept outside the prototype

[SceneMosaic](https://arxiv.org/abs/2609.05594), submitted **4 September 2026**, combines an image-derived candidate with local agentic layout evolution. Its [repository](https://github.com/rxjfighting/SceneMosaic) exposes a GLB export path, but documents Linux/NVIDIA and gated model prerequisites. The potentially useful idea is local variation followed by global revalidation; combining locally valid regions alone cannot guarantee a clear physician route. The project code is [MIT](https://raw.githubusercontent.com/rxjfighting/SceneMosaic/main/LICENSE); model/data/dependency/output rights remain unverified. This stays a later comparison.

[Affordance2Action](https://arxiv.org/abs/2606.04172), submitted **2 June 2026**, grounds task instructions to functional parts, including multiple valid regions in one scene. That could eventually help propose equipment control/access anchors for review. It does not decide the clinical contents or starting state of a room; code/weights/data licensing and adoption readiness remain unverified. These leads broaden the literature search without adding prototype dependencies.

## Proposed changes to the existing architecture

**1. Compile reviewed activities into explainable constraints.** Each required object or relation needs its case activity/rule source, bound runtime identity, required/optional/intentionally-absent classification and measurable acceptance condition. Actor dimensions and selected equipment configuration inform operational envelopes. Clinical reviewers own task requirements and thresholds; household anthropometry is a design lead. Keep the one-room, bounded-anchor resolver first.

**2. Give starting-state requirements explicit evidence.** A small typed contract can express subject, predicate, expected value, provenance, runtime consumer and result: satisfied, unsatisfied, pending or unknown. Pending means an identified consumer is still loading; unknown means no adequate observation yet. Neither permits required-state promotion. “Unknown” must never be coerced to false. Unsupported required states are unsatisfied. These proposed check outcomes are separate from asset-load statuses. The consumer supplies observed evidence, rather than the planner treating its own requested metadata as proof. This is a proposed contract, not a requirement to import BDDL syntax or create a second mutable state store.

**3. Separate proposal scores from acceptance checks.** Validate actual mounted, normalized geometry in the correct coordinate frame; distinguish collision/bounds/opening/route checks from semantic or VLM judgments. Calibrate with known-good and deliberately blocked controls. Bed support, physician anatomical reach and monitor viewing need task-specific checks beyond generic navigability. Do not call every SceneEval metric deterministic, and do not call a solver's own score independent evidence.

These additions attach to existing seams: [scenario authoring](packages/openclinxr/shared-schemas/src/schemas.ts:472), [runtime startup](packages/openclinxr/scenario-runtime/src/scenario-runtime.ts:93), [equipment identities](packages/openclinxr/asset-registry/src/runtime-bundles.ts:85), [equipment normalization](packages/openclinxr/xr-station/src/station-equipment.ts:345), and [semantic zones](packages/openclinxr/asset-registry/src/environment-zone-templates.ts:26). The environment manifest also carries free-text equipment strings, so it does not close the catalogue binding gap. [Manifest schema](packages/openclinxr/shared-schemas/src/schemas.ts:396) Session startup is a state-ownership seam, not a geometry acceptance point. Observe both exits of the [load callback](packages/openclinxr/xr-asset-loading/src/generated-loaders.ts:433): the normal branch mounts normalized geometry; the suppression branch returns before normalization/mounting, so its retained fallback is the realized geometry to inspect. Even `loaded` can describe a suppressed mismatched GLB with a fallback; acceptance needs exact realized identity, fallback status and actual required geometry/state. The main brief records source-inspected gaps and repository revisions. None of these proposed evidence fields or checks is claimed to be wired end to end today.

## Prototype consequences and what waits

Start with the same room, supine patient, physician and case-required equipment. Add one deliberately missing required item, one intentionally absent item, one unsupported required starting state and one blocked approach. Require consumer-observed results and the proposed pre-event readiness/snapshot ordering (not yet established by current startup); never pre-complete a learner connection task. After static placement works, demonstrate physician approach and useful final position while support and equipment checks remain satisfied. Record case/assets/solver versions, variation index, resolved output and starting snapshot.

Function2Scene and Behavior-Aware inform specification and envelope design now; BDDL informs a minimal predicate contract; SceneEval informs test categories. SceneSmith and RoboCasa365 remain later comparison references. HSM, LayoutVLM, Holodeck and the main brief's existing PhyScensis/PlaceIt3D candidates remain useful context, but adding more generators does not close the current authored-intent-to-runtime gap. Avoid requiring CUDA, a new simulator or unrestricted generated rooms to pass the first M1 Max 64GB prototype.
